# Audio-Video Sync Fix - Audio-Driven Pacing

## Problem

Video races ahead of audio, causing:

1. **Growing desync**: video_ts advances faster than audio_ts (e.g., 3200ms difference)
2. **Stuttering playback**: Client struggles to sync mismatched streams
3. **Silence frames**: Audio buffer runs empty

## Root Cause: The Timestamp Trap

### What's Really Happening

The Ditto model assigns timestamps based on **ideal playback time**, not **actual generation time**:

```python
# In Ditto model:
timestamp = frame_idx / 25  # Ideal playback position
```

So even if the model generates 50 FPS (real-time: 20ms per frame), the timestamps are:
- Frame 0: ts=0.000s (generated at real t=0.00s)
- Frame 1: ts=0.040s (generated at real t=0.02s) ← 40ms timestamp gap, but 20ms real time!
- Frame 2: ts=0.080s (generated at real t=0.04s)
- ...
- Frame 10: ts=0.400s (generated at real t=0.20s) ← 400ms of "playback time" in 200ms real time!

Meanwhile, audio arrives in **real-time**:
- Audio chunks arrive every 20ms (browser sends continuously)
- After 200ms real time: Have 10 audio chunks (ts: 0.00s → 0.36s)
- But we have 20 video frames (ts: 0.00s → 0.76s)!

**Mismatch**: Video needs audio at ts=0.76s, but we only have audio up to ts=0.36s!

### Why Frame Dropping Doesn't Work

Initial approach was to drop frames based on timestamps:
```python
# ❌ WRONG: This doesn't work!
if timestamp - last_timestamp < 0.040:
    drop_frame()
```

**Why it fails**: Timestamps are ALWAYS 0.040s apart (by design from model), regardless of how fast frames are actually generated. So this never drops anything!

## The Correct Fix: Wait for Audio

Instead of dropping frames, **wait for audio to arrive before sending video**:

```python
# ✅ CORRECT: In AVSynchronizer.get_next()
video_frame = await video_generator.get_next_frame()

# CRITICAL: Wait for matching audio
while audio_chunk is None:
    audio_chunk = audio_passthrough.get_playback_chunk()
    if audio_chunk is None:
        await asyncio.sleep(0.01)  # Wait for audio to arrive

return (video_frame, audio_chunk)
```

### How It Works

1. **Model generates fast**: 20 frames queued in 400ms
2. **WebRTC requests frame**: "Give me next frame to send"
3. **Get video frame**: Pop from video queue (instant)
4. **Wait for audio**: Check if audio chunk available
   - If yes: Return pair
   - If no: **Wait 10ms and check again** (audio will arrive soon)
5. **Send synchronized pair**: Video + audio with matching timestamps

**Result**: Video output is **throttled by audio arrival rate**, ensuring perfect sync!

### What "waited=Xms" Means

```
✅ Sync #50: ..., waited=0ms    ← Audio ready immediately (plenty buffered)
✅ Sync #100: ..., waited=20ms  ← Waited briefly for audio to arrive
⚠️ Sync #200: ..., waited=100ms ← Model may be too slow OR network lag
```

- **waited=0-50ms**: Normal, healthy operation
- **waited=50-200ms**: Acceptable, may indicate model occasionally slower
- **waited>200ms**: Problem - model too slow or audio network issues

## Performance Characteristics

### CPU/GPU
- **Model runs full speed**: No artificial throttling
- **Video queue builds up**: Shows model is faster than needed (good!)
- **WebRTC paced by audio**: Natural backpressure

### Memory
- **Video queue**: Bounded at 100 frames (~4 seconds @ 25 FPS)
- **Audio deque**: Bounded at 500 chunks (~20 seconds)
- If queues max out: Oldest dropped (shouldn't happen in normal operation)

### Network
- **Smooth transmission**: Consistent 25 FPS output
- **Better quality**: WebRTC can allocate bits efficiently
- **No jitter**: Perfect timestamp alignment

## Monitoring

### Warning Signs

#### Problem: Model Too Slow
```

📊 Generated 100 frames, queue size: 0       ← Empty queue, model can't keep up
```
**Solution**: Optimize model or reduce quality settings

#### Problem: Network Issues
```
⚠️ Sync #X: waited=500ms
📥 First audio frame: (long gap in logs)
```
**Solution**: Check network, firewall, or client issues

#### Problem: Queue Overflow
```
⚠️ Video queue full, dropped 10 frames
📊 queue size: 100/100 (consistently full)
```
**Solution**: Audio isn't being consumed fast enough (unlikely with this fix)

## Why This Approach is Correct

### Alternative Considered: Drop Frames
❌ **Can't work**: Timestamps don't reflect generation rate

### Alternative Considered: Slow Down Model
❌ **Can't control**: Ditto's generation speed is what it is

### Alternative Considered: Re-timestamp Frames
❌ **Breaks sync**: Model's timestamps are authoritative (from audio processing)

### Chosen: Wait for Audio ✅
✅ **Simple**: Just wait until audio arrives
✅ **Correct**: Ensures 1:1 audio-video pairing
✅ **Efficient**: No dropped frames, no wasted work
✅ **Self-pacing**: Automatically matches audio rate

## Summary

**The Fix**: Don't send video frame N until audio chunk N is available.

**Why It Works**:
- Audio arrives at real-time rate (controlled by client)
- Video waits for audio (instead of racing ahead)
- Natural synchronization without manual timing

**Expected Result**:
- diff < 50ms (timestamps match)
- waited < 50ms (audio arrives quickly)
- No silence frames (audio never runs dry)
- Smooth 25 FPS playback

The video queue size indicates how much faster the model is than real-time:
- Queue size ~10-30: Model is 1.5-2x faster than needed (perfect!)
- Queue size ~0-5: Model barely keeping up (may cause stuttering)
- Queue size 100: Model WAY too fast OR audio not being consumed

This is the **correct** approach for audio-video synchronization in streaming systems!
